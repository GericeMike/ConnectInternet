# rdlink 会话交接文档

> **给新机器上的 ZCode**：读这份文档 + `README.md` + `docs/M1-任务拆解.md` 即可无缝接手开发，不需要原始聊天记录。

## 项目是什么

用户要做一个**局域网远程桌面**（对标向日葵/网易UU远程，痛点是延迟），Rust 从零自研，代号 rdlink。已有完整需求调研和架构设计。

- **主控端**：RTX 4060 laptop（多屏，Windows）—— 开发主力机，仓库在 `C:\AI\ConnectInternet`
- **被控端**：MX250（Pascal NVENC，Windows）—— 仓库在 `D:\AI\ConnectInternet`，环境已于 2026-09-29 搭好（见下）

## 需求要点（20 问调研收敛后）

- 同一局域网直连，架构预留跨网能力（M2+）
- 双向控制（对称设计，同一程序切换角色）
- 用途全覆盖：办公（清晰文字）+ 游戏（<35ms 低延迟）+ 写代码 → 双模式设计（M2）
- 1080p60 基线；单人使用；固定密码 + 常规加密；被控端常驻服务（M3）
- 功能：文件传输/剪贴板/电源控制/进程管理（M3）；音频**永久砍掉**
- 关键硬件事实：**被控端 MX250 是弱卡**，编码负载在它身上，1080p60 是甜点，4K 别想

**T7 实现要点（2026-09-29）**：host `serve.rs`（监听循环+捕获线程，tx 经 WGC Flags 注入 handler）+ client `stream.rs`（收流解码工作线程→帧槽丢旧保新→request_redraw 驱动渲染）+ `decoder.rs`。**T7 用软解 h264**（in-band SPS/PPS 自初始化零配置，4060 软解余量足）——Annex-B 裸流与软解兼容性已实测通过；cuvid 硬解留 T9/T10 优化。

**被控端 T7+T8 全链路自测（2026-09-29 被控端）**：`serve.rs` 补上 Input 流消费（原版 `input: _input` 被忽略）→ `input::inject`，新增会话级注入统计；transport 加 `input_probe` 示例（连接后发 5×MouseMove + Shift 按抬）。本机实测：QUIC 握手 → NVENC 拒 → QSV 兜底 → 会话发送 87 帧 + 注入 7 事件 0 拒绝 → 光标实测到位（1135,1078→599,399）→ Bye 优雅回收。**host 侧 T7+T8 闭环完整，等 client 侧输入捕获（winit 事件→Input 流）即可两机真机联调**。

**下一步：T8 client 侧（主控端）→ 两机真机联调（建议插网线）→ T9 打点**（注意：两机时钟不同源，端到端延迟需 Ping/Pong 对时）。

**被控端编码结论（2026-09-29 QSV 实测后，用户已确认接受 60fps 推迟）**：M1 CPU 管线下无 <10ms 编码路径——QSV 瓶颈在同步往返+系统内存拷贝，不在 GPU；NVENC 是唯一 2~5ms 级路径但仍被 R580 驱动拒。出路二选一：**a) 回滚 576.xx 驱动**（B 计划，需管理员，用户决策）；**b) M2 零拷贝 GPU 管线**（D3D11 纹理直喂，省 CPU 侧 ~8-10ms）。M1 期间按 25~40fps 实际帧率继续开发验证。⚠️ 联调前建议插网线（Wi-Fi 弱信号会污染延迟数据）。

**合并时主控端补充的改动**：`--list-monitors` 保留（并入 capture.rs）；`--check` 编码器清单补 h264_qsv，且注明 find_by_name ≠ 能开会话（TODO: open probe）。

## 已踩过的坑（重要，别再踩）

1. **QUIC uni 流必须写首帧对端才可见**——`open_uni()` 不发数据，对端 `accept_uni()` 永远阻塞。解法已实现：video 流首帧=`VideoStreamInfo`，input 流首帧=`InputStreamReady`（见 `session.rs` 握手）
2. **FFMPEG_DIR 必须用 `[env] relative=true`**（`.cargo/config.toml`）——build script cwd 在 registry，纯相对路径解析错位，版本探测出 (0,0)
3. **winget 源可能损坏**（0x80071130）→ 用官方引导器直装（rustup-init.exe / vs_BuildTools.exe）
4. **bindgen 需要 libclang** → `winget install LLVM.LLVM`，路径写死在 `.cargo/config.toml`
5. **thirth_party/ffmpeg 是 gitignored** —— 新机器要按 README 下载 BtbN n8.1 shared 解压到 `third_party/ffmpeg`
6. quinn 的 `SendStream::finish()` 不是 async（0.11）
7. ffmpeg-the-third 导入名是 `ffmpeg_the_third`，版本探测自动从头文件读，**不需要** feature 指定版本

## 被控端（MX250 机）环境记录（2026-09-29 搭建）

验收全过：`cargo test --workspace` 6/6 绿；`host --check` 输出 avutil 60.26.103 + h264_nvenc/libx264 可用。本机特殊点：

8. **本机无管理员权限装 LLVM** → LLVM 23.1.2 MSI 用 `msiexec /a`（管理模式解包）解到 `C:\Users\<user>\LLVM`，`setx LIBCLANG_PATH C:\Users\<user>\LLVM\bin`（用户环境变量，持久）。cargo 的 `[env]` 默认不覆盖真实环境变量，所以 `.cargo/config.toml`（指向 Program Files，主控端用）**不用改**
9. **本机 `System32\nvEncodeAPI64.dll` 缺失**（驱动安装不完整，581.80 版本号本身够）→ 从 `DriverStore\FileRepository\nvqui.inf_*` 复制同版本 DLL 到 `third_party/ffmpeg/bin/`，LoadLibrary 按 exe 目录优先命中（符合 D7）
10. **⚠️ R580 驱动（581.80）拒绝 Pascal 的 NVENC 会话**：DLL 正常加载（Nvenc 13.0、识别 MX250 SM 6.1），但 `OpenEncodeSessionEx` 返回 *unsupported device*。R580 是 Maxwell/Pascal/Volta 最后分支（2025-10 后 legacy），社区确认 580 系不再给 Pascal 开 NVENC。**`--check` 只查注册表所以显示"可用"，T4 实际开编码器会失败**。预案（T0 风险表命中）：
    - a. 回滚 NVIDIA 驱动到 576.xx/577.00（需管理员，用户决策）
    - b. 直接走 T4 已设计的 libx264 ultrafast+zerolatency 兜底分支（MX250 本子 CPU 1080p60 大概率吃力，实测才知道）
11. 本机 VS 是 Professional 2022（装在 D 盘，含 MSVC 14.36 + Win10 SDK 22000），无需再装 Build Tools
12. **WGC 黄边去不掉**：`DrawBorderSettings::WithoutBorder` 在消费版 Win10 19045 报 `BorderConfigUnsupported`（`IsBorderRequired` 需 build 20348+，即 Win11/LTSC）。但实测 `Default` 设置下捕获帧**并没有黄边**，像素边缘干净——问题不存在，别再折腾
13. windows-capture 2.0.1 API 与老教程不同：`GraphicsCaptureApiHandler` trait + `Settings::new(monitor, cursor, border, secondary, min_update, dirty, color, flags)`（Monitor 直接当 item 传入，无需 picker）；CPU 帧用 `frame.buffer()` → `FrameBuffer`（有 `row_pitch()`，T4 可用 pitch 喂 av_frame 免二次拷贝）；PNG 用 `frame.save_as_image(path, ImageFormat::Png)`（Bgra8→PNG 通道序正确，已肉眼验证）
14. WGC 脏区驱动在被控端实测：桌面有活动时 90~119fps（光标也计入脏区，光标动 = 出帧）；静止秒 = 0 帧。M1 决策保持：client 保最后帧，心跳帧后补
15. **x264 码率控制坑**：time_base=1/1_000_000 且不声明帧率时，x264 把 1µs 当帧时长 → 每帧码率预算 = 50Mbps×1µs = 50bit → QP 崩 51、P 帧 100% skip、画面全是色块。修复：`set_frame_rate(Some((60,1)))` 声明名义 60fps（串流标准做法），time_base 保持微秒。修复后 QP 8.5、I 帧 286KB、P 帧可辨文字
16. **裸 .h264 流没有 pts**：Annex-B 裸流不存时间戳，ffprobe 显示的 pts 是它按探测 fps 编的帧号——排查 pts 问题时别被它误导（用编码器回调里的 packet.pts() 验证）
17. ffmpeg-the-third 6.0.0 编码 API 要点：`Context::new_with_codec(codec).encoder().video()` 得 builder；`open_as_with` 返回 `video::Encoder`（注意 video.rs 里有个同名包装类型，别和模块级 `Encoder` 搞混）；BGR0 的 Pixel 枚举名是 **`BGRZ`**；libx264 只吃 YUV 系像素格式（**bgr0 只有 NVENC 支持**），x264 路径须 swscale 转换
18. ffmpeg 编码器类型无 Send（仅 Packet 有），跨线程移动用 `unsafe impl Send` 包装（纯所有权转移，见 encoder.rs SendEncoder）
19. **被控端 Intel 核显 QSV 硬编已落地**（`QsvEncoder`，三级兜底 NVENC→QSV→x264 实测全链路生效）。但 M1 CPU 管线下编码耗时 p50=21.1ms/p95=32ms（async_depth=1 同步往返 + 8MB copy + swscale；low_power/VDENC 与 FAST_BILINEAR 只边际改善），**不优于 x264 软编（16.8/22ms），价值在 CPU 卸载**。QSV 画质验证通过（P 帧文字可辨）
20. **QSV `scenario` 选项是整数枚举**：字符串常量名（如 "display_remoting"）会被当表达式解析直接报错，须传数字（1 = MFX_SCENARIO_DISPLAY_REMOTE）
21. **ffmpeg 的 nvenc 加载器不搜 PATH**：`LoadLibraryEx(LOAD_LIBRARY_SEARCH_SYSTEM32|APPLICATION_DIR)` 只搜系统目录和 exe 自己的目录——所以 `nvEncodeAPI64.dll` 必须复制到 `target/release/`（exe 旁），PATH 里有也没用；CLI 测试能过是因为 ffmpeg.exe 就在 DLL 旁边。avcodec-62.dll 等常规 DLL 走正常搜索不受影响
22. QSV 系统内存模式的 submit→receive 是同步往返：严格逐帧"提交即等"测出的是单帧真实延迟（好），但也放弃了流水线吞吐（CLI 默认 async_depth=4 时 76fps 就是这么来的）——M2 若要吞吐可改流水线提交

### 主控端 client 侧（T5/T6，主控端会话补充）

23. **NVDEC 硬解用 h264_cuvid（全硬解 codec）而非 d3d11va hwaccel**：cuvid 解码输出直接是系统内存 NV12，无需 get_format 回调/hw_frames_ctx 拆腾，`find_by_name("h264_cuvid")` + `open_as` 即用；软解兜底用 `Context::from_parameters` 默认 codec。首包含 cuvid 初始化冷启动（~0.6s），稳态 p50 2.9ms
24. **wgpu 30 API 大改**（旧教程全部失效）：`present` 从 SurfaceTexture 挪到 `Queue::present(tex)`；`get_current_texture()` 返回 `CurrentSurfaceTexture` 枚举（Success/Suboptimal/Timeout/...）；`SurfaceConfiguration` 新增 `color_space`（用 `Auto`）；`bind_group_layouts` 是 `&[Option<&BGL>]`；`multiview_mask` 是 `Option<NonZero<u32>>`
25. **debug/release 差异极大**：CPU 生成测试图 debug 27fps → release 230+fps；**所有性能测量必须 release 构建**。winit 0.30 用 `ApplicationHandler`（resumed/window_event），窗口 Arc<Window> 交给 wgpu `create_surface`
26. **被控端系统 PATH 里有另一套 FFmpeg**（`D:\FFmpeg\ffmpeg-master-latest-win64-gpl-shared\...\bin`，master 构建）：给 cargo run/test 前缀 PATH 时**必须用绝对路径**——相对路径前缀在 cargo 的子进程 cwd 下失效，DLL 搜索会落到系统 PATH 那套旧 DLL 上，报 `STATUS_ENTRYPOINT_NOT_FOUND`（0xc0000139），极易误判成代码问题

### 被控端 T8 输入注入（2026-09-29 被控端会话补充）

27. **T8 host 侧已落地**：`input.rs` 的 `inject(&InputEvent)`（SendInput 全覆盖：绝对坐标鼠标/五键/滚轮/VK/扩展键/Unicode），`--input-demo` 自测 6/6 PASS（坐标回读误差 ≤1px、按键状态验证）。扩展键集合是白名单 `EXTENDED_VKS`（方向键/PgUp/PgDn/Home/End/Ins/Del/小键盘除号/右Ctrl/右Alt/Apps/PrtScn/NumLock），漏带 `KEYEVENTF_EXTENDEDKEY` 是任务卡标注的经典坑，已在注入器内统一处理
28. windows 0.62 绑定差异：`SendInput(&[INPUT], cbsize)` 收不可变切片（不再要 len 参数）；`MOUSE_EVENT_FLAGS`/`KEYBD_EVENT_FLAGS` 是 newtype（BitOr 已实现）；`WHEEL_DELTA` 在 `WindowsAndMessaging` 不在 `KeyboardAndMouse`；无 `Error::from_win32()`，用 `Error::from_hresult(HRESULT::from_win32(GetLastError().0))`

## 架构速览

```
client(4060): winit/wgpu 渲染 ← NVDEC 解码 ← QUIC Video 流（可靠 stream，M1 决策 D1）
client → Input 流（键鼠事件）→ host: SendInput 注入
host(MX250): WGC 捕获 → NVENC(bgra 直喂, preset p1 + tune ull) → Video 流
三通道: Control(bi) / Video(uni host→client) / Input(uni client→host)，length-prefix + bincode
证书: rcgen 运行时生成 + SHA-256 指纹 pin（决策 D5）
```

决策记录 D1~D7 见 README。任务细节见 docs/M1-任务拆解.md。
