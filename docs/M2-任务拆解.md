# M2 任务拆解：延迟优化

目标：局域网 e2e p50 ≤ 12ms、运动场景 60fps、热会话首帧 ≤ 500ms（已达标 ~380ms）。

当前基线（2026-09-29，被控端实测）：e2e p50 16-19ms / rtt 2-8ms / ~35fps / enc p50 17ms（拷贝 1.9 + swscale 10 + QSV 5）。

> 结构说明：原 M2-1（首帧）已完成，见 docs/M2-进展.md。剩余任务按性价比排序，
> 主线是 T2（NV12 直采直喂），T3（真零拷贝）是 T2 不够时的深水区备选。

## T2（主线）：NV12 直采直喂，砍掉 swscale 10ms【host 侧】

思路：与其采 BGRA 再 CPU 转 NV12，不如让 WGC 直接以 NV12 采集（DWM 在 GPU 合成时
顺带完成 420 下采样——和现在 swscale 干的事等价，理论零画质损失），readback 直接
得 NV12（3MB 而非 8MB，拷贝也省一半），三档编码器全部原生吃 NV12。

- **T2.1**（前置验证，~1h）：确认 windows-capture 2.0.1 的 `ColorFormat` 是否暴露 NV12
  （读 crate 源码；没有则评估 fork 加枚举 vs 放弃 T2 改走 T3）。
- **T2.2**（捕获改造，~0.5 天）：`serve.rs`/`capture.rs` 切 NV12 采集；双平面
  readback（Y 平面 + 交错 UV 平面）按 stride 逐平面拷入 ffmpeg `Video(NV12)`。
  风险：windows-capture 的 FrameBuffer API 对 planar 格式的适配方式未验证，
  可能需要绕行纹理级 readback。
- **T2.3**（编码器改造，~0.5 天）：trait 签名从 BGRA 改 NV12；`QsvEncoder` 删
  scaler 直喂；`X264Encoder` 兜底也改直喂（libx264 原生支持 nv12，一并受益）；
  `NvencEncoder` 同步切换（未来驱动回退解锁后直接受益）。
- **T2.4**（画质回归，~0.5h）：文字/代码场景对比截图，确认 420 直采与
  BGRA→NV12 视觉无差。
- **T2.5**（测量验收）：分段计时复测。预期 enc 17ms → **~6.5ms**
  （拷贝 ~1.5 + 0 + 5）；稳态 fps 应到 55-60。
- 验收线：enc p50 ≤ 8ms；运动场景 ≥ 55fps；画质无肉眼可见退化。

## T3（备选深水区）：D3D11 零拷贝 GPU 管线【host 侧，仅当 T2 后仍不达标】

T2 之后剩余 CPU 成本只有 NV12 readback ~1.5ms + QSV 提交 5ms。若 readback 或
DWM 合成成为 60fps 的挡路石，再上真零拷贝：WGC 的 D3D11 纹理全程留在 GPU。

- **T3.1**（绑定调研，~0.5 天）：ffmpeg-the-third 对 `AVHWDeviceContext`/
  `AVHWFramesContext`/derive（d3d11↔qsv）的暴露程度；不足则下探 ffmpeg-sys-next
  裸 API（预期大概率走 sys-next）。
- **T3.2**（会话共设备）：从 WGC 纹理取 `ID3D11Device` → 建 d3d11 hwdevice →
  derive QSV（QSV 会话复用同一设备，避免跨设备共享句柄）。
- **T3.3**（纹理直喂）：`CopySubresourceRegion` 拷入 QSV surface pool（GPU 内
  ~0.1-0.5ms）→ 若直采 NV12 则免 VPP；BGRA 则需 VPP 转换。
- **T3.4**（生命周期）：d3d11 锁、surface 复用、与编码器 async_depth 的同步。
- 预估 2-4 天；预期 enc → 2-4ms。**触发条件：T2.5 实测 60fps 仍不可达。**

## T4：60fps 端到端验证（依赖 T2）

- 持续运动场景（远程拖窗/播视频 + jiggle.ps1 保底）跑 ≥10min：fps、丢帧、
  背压队列、e2e p50/p95 全录。
- 必要时调发送通道容量/丢帧策略（channel(4) 的 4 是否还合适）。
- 验收：运动场景 ≥55fps 且 e2e p50 ≤ 12ms。

## T5：NVDEC 硬解【client 侧，低优先，默认砍】

dec 已 1-2ms。只有当主控端 CPU 占用影响多开/别的任务时才值得做。挂在 M4 一并考虑。

## T6：基线复测 + 文档

- 更新 docs/M2-进展.md（分段计时新数据）、docs/M1-基线数据.md 追加 M2 对照列。
- 长稳冒烟 ≥30min（对齐 M1 的 32.7min 标准），零错误 + 丢帧在背压设计内。

## T7：（暂缓）驱动回退 576.xx 解锁 NVENC

用户已决策暂缓。若 T2/T3 后延迟仍不满意，再评估。T2.3 已让 NVENC 档兼容 NV12
直喂，届时回退即插即用。

## 执行方式备忘

M2 全部工作在 host 侧。主控端会话经 SSH 已可独立完成被控端的拉码/构建/部署/
测试/日志闭环（2026-09-29 验证 3 轮），无需被控端 ZCode 会话参与；其会话可作
review 用。
