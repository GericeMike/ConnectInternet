> 协议现状 v7。性能基线：e2e 13-15ms / 60fps / 链路瓶颈在 Wi-Fi。

## T1 IME 中文注入（1 天）✅ 完成（2026-10-02）

- client：winit `WindowEvent::Ime(Ime::Commit(text))` → 逐字符发 `InputEvent::UnicodeChar`；
  组字期间（非空 Preedit）抑制物理键转发防字母泄漏。
- host：SendInput `KEYEVENTF_UNICODE`（含 UTF-16 代理对拆分，emoji 可注入）。
- **实测补的两个坑**：① winit 0.30 Windows 端窗口默认摘除 IME 上下文，必须
  `set_ime_allowed(true)` 否则 Ime 事件不来；② 物理键抑制窗口必须是"组字进行中"
  而非"IME 开启"——否则输入法开着时 Enter/Backspace/方向键全被吞。
- E2E：Win+Space 切微软拼音打"你好世界"两轮上屏、无字母泄漏、组字后数字/英文
  物理键正常。emoji 走同一代码路径（代理对），留待日常使用确认。
  （备注：以 PostMessage 自动化切输入法会卡死 winit UI 线程（WM_INPUTLANGCHANGE
  的 DefWindowProc 不返回），真实 Win+Space 路径无此问题。）

## T2 多显示器 + DPI（2 天）✅ 完成（2026-10-02，协议 v8）

- T2.1 枚举与选择 ✅：协议 v8 `MonitorListReq/MonitorList/MonitorSelect`；client
  **F10 热键轮换显示器**（会话内热切不重连）；`[host] monitor_index` 配置默认屏。
  本地双屏回环实测：1080p↔1440p（负坐标副屏 -2560,-416）切换不断流。
- T2.2 跨屏映射 ✅：host 输入注入改 `MOUSEEVENTF_ABSOLUTE|VIRTUALDESK` 全虚拟
  桌面归一化（ACTIVE 矩形由 monitors.rs 登记，支持负坐标副屏）。远端 E2E：
  迁移后点击中心 720p→(640,350)、1080p→(960,540) 精确命中。
- T2.3 DPI ✅：host 启动即 `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)`；
  client winit 自带 PMv2。混合 DPI 坐标映射数学已按虚拟桌面物理像素实现，
  真机混合 DPI 验证依赖用户外接屏环境。
- T2.4 动态分辨率迁移 ✅：实测发现 **WGC 帧池不随显示模式缩放**（改分辨率后
  画面会一直按旧尺寸缩放发送，旧实现根本不触发尺寸变化）→ host 加 2s 活动矩形
  监视器（设备名比对，位置/尺寸变化都覆盖），变化即会话内重建捕获（与切屏共用
  `rebuild_capture`）；帧尺寸直变场景另有捕获线程内原地重建编码器+GPU 转换器
  兜底 + VideoStreamInfo 随视频流保序下发（client 热更新解码/映射，全程不断流）。
  远端 E2E：1920x1080↔1280x720 双向迁移无断流、无重连、信令及时、映射精确。
  附带产出：`host --set-res W H` 运维子命令（PS 改分辨率踩了 DEVMODE 编组/dmSize/
  会话权限三个坑后改用 Rust 实现）。

## T3 码率自适应 + 传输隔离（1.5 天）✅ 完成（2026-10-02，协议 v9）

- T3.1 链路感知降档 ✅：client 每 2s 回传 `LinkQuality{e2e_p95_us, recv_fps}`；
  host 滞回升降（p95>100ms×3 连发降一档 / <50ms×15 连发升一档，仅 recv_fps≥5
  时判定——静止桌面分位数无链路意义）；档梯 [基础档,30,15,8] Mbps。
- T3.2 传输隔离 ✅：双管齐下——①**工具连接不抢占**（协议 v9 `Hello.is_tool`，
  --upload/--procs 走仅控制流+文件流的轻会话；实测原实现 CLI 传输会抢占视频
  会话造成重连风暴，这才是"传文件视频卡"的主因）；②传输进行中全局计数
  （filex ACTIVE_TRANSFERS）→ 档位压 ≤15M，传完恢复。
- 码率热切实现：TIER_BPS 全局原子量，捕获线程每帧比对、变化即按新码率原地
  重建编码器（ffmpeg 硬编打开后改 bit_rate 不生效；~200ms+IDR，≥2s 防抖）。
  **坑**：基础档 store 必须先于 start_capture——竞态下读到 0 被 max(1) 污染成
  1bps，QSV/x264 全崩 → host panic → supervisor 循环重启 → 主控端重连风暴。
- E2E：本地回环 800MB（档位 50→15→50 三段日志+重建全程可见，视频 59fps 无
  重连）；真实 Wi-Fi 200MB/47.6s（~35Mbps 链路占用）期间视频最低 13fps 仍可
  操作、e2e p50 31ms、零重连，传完恢复 45fps；远端 host 日志确认 [tier] 联动。
  弱信号限速 20Mbps 场景留待真实弱网自然验证（T3.1 机制与 T3.2 共享同一
  重建路径，已由传输拥塞场景间接覆盖）。

## T5 文件剪贴板（1 天）

## T6 系统键转发（1 天）

- Alt+Tab / Win 键 / Ctrl+Alt+Del 组合的处理策略：

## T8 跨网访问 → 升级为 M5（独立里程碑）

原始需求"预留跨网能力"。体量大（中继服务器/打洞/安全暴露面），不建议塞进 M4：
- 方案选型：自建中继（VPS+QUIC 转发） vs P2P 打洞 vs Tailscale 组网 vs FRP。
- 认证基础已有（证书 pinning + 密码认证 v7），跨网必须启用密码 + 强制改默认密码。
- 安全评审：暴露面/审计/防爆破（M3-5 已有 3 次失败冷却，需加固为持久封禁）。
建议 M3 收官稳定运行一段时间后单独立项。
